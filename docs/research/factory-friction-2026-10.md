**결론 2.** 엔진 결함은 거의 전부 **한 과(科)**다 — "러너가 만든 상태(미러·overlay·인덱스·크래시 런·검색 색인 지연)를 에이전트의 것으로 오인하거나 그 반대". 12번째까지 왔고 패턴이 같으니 하나하나 고치는 대신 **원인 하나를 끊는** 것이 맞다: 판정이 git 인덱스·검색 색인·스테이지 간 공유 상태를 읽는 자리를 없애거나 단일 함수로 모은다(§3-D).

## 2. 세 불만을 원인에 대응시키면

### "직관적이지 않다"
- 입력: `[ready]` + done_when + `test_<이슈번호>_…` 이름(번호를 **생성 전에** 맞혀야 한다 — 사흘 동안 두 번 틀려 이슈를 닫고 다시 만들었다) + must_not + 경로 언급만으로 NEVER_AUTOMATE에 걸리는 큐 심사(own-cal #122·#123) + `transition.js <n> factory:queue` 호출. 단일 에이전트에게는 "이거 고쳐"로 끝나는 일이다.
- 상태 전이가 **하나의 사실**이 아니다: 재시도·재큐·dispatch·sweeper 복구·라벨 수리 — 같은 "다시 돌려"가 다섯 경로이고 각각 다른 카운터(K·R·예산·재시도 마커)를 건드린다. 운영 세션도 사흘째에야 "재큐가 맞다"를 알았다.

### "가시적이지 않다"
- 이슈 페이지는 기계 코멘트 29개(중앙값)로 덮이고, 사람이 알고 싶은 것 — **지금 어디에 있고, 왜 멈췄고, 내가 뭘 해야 하고, 얼마 썼나** — 는 어디에도 한 줄로 없다. 보드는 있지만 별도 프로세스·tailnet이 필요하고 "왜"는 보여 주지 않는다.
- 사람이 해야 할 일의 목록이 대화(운영 세션)에만 있다 — 세션이 없으면 아무도 모른다.

### "더 나은 개발이라는 확신이 없다"
- 공장이 단일 에이전트보다 **더 한 것**(리뷰어 5명이 실제 결함을 잡은 횟수, 증명된 테스트, 돌연변이 검사, 범위 밖 변경 거부)이 **PR에 적히지 않는다**. PR 본문은 빌더의 산문이고, 증거는 run 기록 브랜치의 수백 줄 안에 흩어져 있다.
- 반대로 공장이 **깨진 것**은 매우 잘 보인다(40번의 needs-human). 성공은 조용하고 실패는 시끄러운 비대칭 — 확신이 생길 수 없는 구조다.
- 실제로 공장이 잡은 것(기록에서): #147 backPressure 예외의 반쪽 복구, #157 재실행이 옛 리포트를 읽는 결함, #149 두 목록·범위 밖, #170 두 번째 파서, #178·#179 각 라운드의 must_fix, own-cal #114·#115 라운드 2의 반려 — **리뷰가 실제 결함을 잡은 사례는 많다.** 보이지 않을 뿐이다.

## 3. 개선안 (구조 순)

**A. 하나의 상태 카드 (가시성).** 이슈마다 러너가 **한 코멘트를 편집**한다(새 코멘트가 아니라): 지금 단계·시작 시각·누가(런 id)·무엇을 하는 중(진행 마커 요약)·막혔으면 **왜**와 **사람이 할 일**(정확한 명령 한 줄)·라운드 K/R·평생 비용·마지막 3개 이벤트. 기계 마커 코멘트는 그대로 남기되(기록이다) 카드가 맨 위에 고정(`gh api … /issues/n/comments` 첫 코멘트를 갱신). `factory status`(CLI)는 두 저장소의 카드를 한 표로. 사람 몫은 **이슈가 아니라 카드가 말한다** — 운영 세션이 없어도.

**B. 증거 블록 (확신).** merge 스테이지(또는 리뷰 승인 시점)가 PR 본문 끝에 러너 작성 섹션 `## Factory evidence`를 **덧붙인다**: done_when ↔ 테스트 표(prove-test 통과 여부), 리뷰 라운드별 역할·판정·must_fix와 그것이 어느 커밋에서 고쳐졌는지, 게이트(레벨·GREEN/RED·재실행), 돌연변이/가드 결과, 거부한 범위 밖 변경, 비용·소요. 머지 뒤 이슈에도 같은 요약 한 코멘트. "단일 에이전트였으면 그냥 머지됐을 것"이 무엇이었는지가 거기 있다.

**C. 입력의 단순화 (직관성).** (1) `test_<n>_` 번호 맞히기 폐지 — 이슈 본문의 `test_NNN_`/`test_<n>_`을 **triage가 번호로 치환**하고(이슈 본문 편집은 러너 몫) 검증기는 치환 뒤를 본다. (2) 큐 심사의 NEVER_AUTOMATE 대조는 `## Impact paths` 섹션의 경로만 본다 — 본문 다른 곳의 언급은 세지 않는다. (3) `know-thy-build:issue` 스킬이 **한 문단 요청 → 구조화 이슈 초안 → 확인 → 제출**을 한 번에 한다(이미 있으면 그 경로를 문서화·고정). (4) "다시 돌려"는 **하나**: `factory retry <n>` — 사람이면 중단 지점 재개, 에이전트면 재큐, 둘 다 같은 명령; 카운터(K·R·예산)는 **엔진 결함으로 판정된 런을 제외**하고 센다(§D).

**D. 같은 과의 결함을 끊는다 (신뢰).** 12개 결함의 공통 원인 = 판정이 "현재 체크아웃 상태"를 여러 경로(인덱스·워크트리·검색 색인·캡처된 변수)로 읽는다. 조치: (1) 미러·overlay·drift 판정을 `lib/tree-truth.js` 하나로 모아 **HEAD 트리와 생성물만** 비교(인덱스·워크트리 상태 불참) — 1.4.38·1.4.44·#162가 각각 땜질한 자리를 하나로. (2) sweeper의 모든 전이는 실시간 라벨 재확인 뒤(#176의 원칙을 전 팔에). (3) **엔진 결함으로 죽은 런은 이슈의 카운터(K·R·평생 예산)에 세지 않는다** — `abortStage`가 "엔진" 등급(미러 판정 불가·크래시·harness undefined)으로 남긴 런은 `budget`·`reviewRounds`·`retries`에서 제외. 지난 3일의 C·D 9회가 전부 이것이다.

**E. 빌더 품질 (K 소진).** rework 라운드 ≥2에서는 **빼는 것만** 허용: 새 파일·새 export·새 done_when → self-gate RED(#174의 브리프 규칙을 모든 rework에). 리뷰어 must_fix에 `where`가 있으면 그 파일 밖 변경도 RED.

**F. 정직한 측정.** 위 A·B가 들어온 뒤 2주의 수치(needs-human 횟수·사람 행동 횟수·큐→머지·이슈당 비용·리뷰가 잡은 결함 수)를 `docs/factory/health`에 주간으로 남긴다 — "더 나은가"는 이 표가 답한다.

## 4. 우선순위(제안)
1. **A 상태 카드 + C-(4) 단일 retry + D-(3) 엔진 결함 런 제외** — 사람 몫과 혼란을 바로 줄인다.
2. **B 증거 블록** — 확신의 재료.
3. **C-(1)(2)(3)** — 입력 마찰.
4. **D-(1)(2), E** — 결함의 과를 끊고 K 소진을 막는다.
5. F — 측정.
