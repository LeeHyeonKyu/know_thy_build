## 2. 운영 세션 규칙 (A — 즉시, 문서·메모리만)

- **A1 승인 PR의 충돌은 운영 세션이 리베이스해 door로 넣는다.** 공장 재큐는 "코드가 바뀌어야 할 때"(리뷰 거부·결함)만. 리베이스 뒤 범위 테스트 GREEN이면 PR 본문에 "operator rebase: 충돌 파일·hunk 수"를 적고 머지. (이번에 9건을 재큐해 ≈ $150·15h를 썼다.)
- **A2 모니터는 종료 상태 1종(merged / needs-human / blocked)만, 간격 ≥ 15분, 한 번에 여러 이슈를 한 모니터로.** 진행 보고는 상태가 바뀐 때만 한 줄.
- **A3 조사·리뷰는 서브에이전트 1회**(브리프 ≤ 300자, 결론 ≤ 200자, 읽기 전용). 메인 세션은 결정·실행만 한다. 로그·기록 grep을 메인에서 반복하지 않는다.
- **A4 메인 컨텍스트가 150k를 넘으면 `/compact`를 요청**하거나 새 세션으로 교체한다(캐시 읽기 439M의 뿌리).
- **A5 대역 리뷰는 판정 로직 엔진 변경에만**(#294 반영 완료). 테스트 핀·문서·재착륙·설정 숫자는 운영 세션이 읽고 PR 본문에 적는다.
- **A6 사람 몫은 세션당 한 번만 한 줄로.** 반복 보고 금지.

## 3. 공장 구조 (B — 이슈로 공장에)

- **B1 러너 자체 base 머지(에이전트 0).** merge 스테이지가 CONFLICTING을 보면 러너가 `git merge origin/main`을 시도한다. **충돌 hunk가 없으면** 러너 커밋으로 push → 게이트 재실행 → 창 → 머지(리뷰 재실행 없음: diff가 승인 head + base뿐이다). 충돌 hunk가 있으면 오늘의 conflict-only 라운드(#212/ADR-041). 이번 체인의 재큐 9건 중 git 자동 머지로 끝났을 것이 7건. **새 이슈.**
- **B2 예산 상한은 "새 에이전트 라운드 시작"만 막는다.** 이미 push된 head의 리뷰·검증·머지는 완주한다(머지 스테이지는 $0). 상한에 걸려 리뷰 직전에 멈추면(#236: $61.54, awaiting-review) 지금까지 쓴 돈이 전부 버려진다. **새 이슈.**
- **B3 재착륙 fast path**(#293, 큐 투입 완료): 승인된 head를 가리키는 이슈는 plan 토론을 건너뛴다.
- **B4 디스패처 페이로드 자가 로드**(#288, PR #302 — H5로 door 대기).
- **B5 거부권 창 15분**(#294 반영). 비판정 경로는 5분으로 더 줄일지는 소유자 결정 — 이 계획은 15 유지.

## 6. 토론 질문 (/333)

1. A1(운영 리베이스 → door)은 "리베이스된 코드는 리뷰를 다시 받아야 한다"는 ADR-033의 정신과 충돌하는가 — 어디까지가 "코드가 바뀌지 않은 리베이스"인가.
2. B1(러너 자체 base 머지)이 리뷰 없는 머지가 되는 경계: git이 자동 병합한 hunk는 리뷰 대상인가. 게이트 GREEN이면 충분한가.
3. B2(상한은 새 라운드만 막는다)가 상한의 의미를 무력화하는가 — "완주 비용"의 상한은 따로 둬야 하는가.
4. 목표 수치(§1)가 현실적인가, 무엇이 먼저인가.
